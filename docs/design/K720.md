# K720: sound off opens no audio

Ledger: K720. One stage, opus, 2 h cap (expect about an hour).

## The bug

With sound off (`soundMode` none, or the mute setting), the first touch
still creates and resumes an `AudioContext`: the autoplay gate's handler
in `src/audio/knot_synth.ts` calls `ensure()`, and plucks reach
`resume()`. Every play path is gated (`settings.muted ||
params.soundMode === "none"`: main.ts, `auto_audio.ts`,
`input_pointer.ts`), so nothing sounds. But a running context keeps the
phone's audio output awake (battery), and on Android it may take audio
focus from Levi's audiobook. Found by the K717 phone sitting
(`.claude/rules/probes-phone.md`, the K704 gotcha).

## The rule to build

No `AudioContext` exists until something actually plays:
- The first activating input only records that the gate is open (the
  page now has a user activation). It creates nothing.
- The context is created at the first real play: a pluck, a song note,
  the snore or any other sound, with sound on. After a user activation
  Chrome starts a new context running, so a later creation needs no
  gesture of its own. Check this in the browser.
- Turning sound on later (the panel) needs no reload: the next play
  creates the context.
- Today's behaviour with sound on stays as it is: with the default sound
  mode, the first touch still opens audio as promptly as today, and
  music mode's song clock switches to the audio clock as today.
- Separate "the gate is open" from "a context exists" wherever callers
  read one to mean the other (`snore_sfx.ts`, `song_scheduler.ts`'s
  clock switch, `auto_audio.ts`'s pre-gate path). Keep each sound's own
  rules, such as whether the snore plays under none; only the moment the
  context is created changes.

### What landed

- `soundIsOn(muted, soundMode)`: sound is off when Muted or sound mode
  none. Volume 0 counts as on (it plays silently, as before).
- `KnotSynth.setSoundOn(fn)` installs the live test. `app/auto_audio.ts`
  installs `soundIsOn(settings.muted, params.soundMode)` before any input
  can arrive. Until something installs one it reads true, so tests,
  probes and an injected context behave as before.
- The gate and the context are separate. `unlocked` records that an
  activating input came (or sticky activation at construction).
  `ensure()` is the one place a context is made, and it returns null
  while the gate is closed or sound is off. The gate's listener
  (`openGate`) sets `unlocked` and calls `ensure()` only with sound on,
  inside the gesture as before. The listeners now disarm once a context
  RUNS (before: at the first input), so a context made later, outside a
  gesture, is resumed by the next input where a browser needs that.
- `pluck()` and `playSample()` go through `ensure()`, so with sound off
  nothing plays, even on a context that already exists.
- `open()` makes the context if it may, and says whether one exists.
  Music's tick calls it before `audioTime()`; the snore's `play()` calls
  it when there is no buffer yet. `whenOpen(cb)` waits for a context,
  not the gate. `decodeSample` is `ctx ?? ensure()`.
- `snore_sfx.ts`: the decode waits on `whenOpen`. A play with no buffer
  calls `host.open()`, then preloads. Its own rules are unchanged:
  silent under Muted, none or volume 0, checked at play time.
- `song_scheduler.ts`: comments only. Its clock switch keys on
  `audioTime()` turning non-null, which now means a context exists.
- With sound on nothing changed: the gate's listener makes the context
  inside the first activating input (pointerdown for a mouse, pointerup
  for a touch), and music's song moves to the audio clock there.
- Tests: `knot_synth.test.ts` "sound off opens no audio (K720)", 15
  cases (none and Muted make no context through the gate and plucks;
  sound on then a pluck makes exactly one; unmuting then a song note
  makes one; the default mode makes one at the first touch, inside it;
  an untrusted input opens nothing; with sound off an existing context
  plays nothing; the listeners stay until a context runs; a refused
  resume runs at the next input (iOS); `whenOpen`; `decodeSample`;
  sticky activation; `userActivation`'s transient flag; an injected
  context). `snore_sfx.test.ts`: the fake host gained `open()`, plus
  three K720 cases (a play makes the context it needs; a play with
  nothing preloaded makes it, then loads; a silenced play makes nothing
  and fetches nothing).

### The browser check

How it counted (K726's Part 3 can reuse the `INSTRUMENT` string at the
top of `.claude/probes/K720/k720_probe.mjs`):
- An init script (`evaluateOnNewDocument`) replaces `window.AudioContext`
  with a subclass that counts constructions. It records each one's
  state, `window.event.type` and `navigator.userActivation` at that
  moment, and wraps `AudioContext.prototype.resume` to count calls. The
  app constructs only `AudioContext`, never `webkitAudioContext`.
- Every read is a raw CDP `Runtime.evaluate` with `userGesture: false`.
  Puppeteer's `page.evaluate` sends a user gesture, which gives the page
  an activation. `window.__knotSynth` stays undefined while no context
  exists, which makes a quick check.
- Panel rows were set by script: untrusted change events open no gate.
- Inputs are real: puppeteer mouse clicks and drags, and CDP
  `Input.dispatchTouchEvent` taps.
- The browser: headed Chrome 155 off-screen, in real time, with a fresh
  profile and a fresh browser context per case. 1400x900 with touch
  emulated, and `--mute-audio` (the analysers still read).

### Residuals

1. SIDE EFFECT, for Levi: the minotaur's cues (the catch notes, growl,
   heartbeat and footsteps: bare `synth.pluck` calls in main.ts) never
   checked Muted or none, because Muted is read per call, not applied as
   a master gain. They sounded under both. With K720 they are silent with
   sound off, like every other sound. This is from the code; no chase
   was probed.
2. The daily's address-bar rewrite drops `snd` (K717), out of scope.
   Options: keep `snd` (or every DAILY_EXEMPT_KEYS preference) in the
   rewritten daily address; persist the sound mode as a localStorage
   viewer preference, as Motion is; or document it.
3. iOS is unverified. A context made outside a gesture (the panel's
   switch, a song tick, the snore's decode) relies on the still-armed
   listeners resuming it at the next input. The Node test covers the
   logic, but neither of Levi's devices is iOS.
4. Volume 0 does not count as sound off: a volume-0 page still makes a
   context at its first input. The brief named only none and Muted.
5. Turning sound off after a context exists leaves it running, which
   costs the same battery and audio focus as the original bug. Idea:
   suspend the context when sound turns off and resume it on the next
   play.
6. The first snore play after sound turns on in manual mode makes the
   context and is silent (the decode starts then); the next play sounds.
   Before K720 that corner played, since the first click had made a
   context. The lore's open idea, decoding on an OfflineAudioContext,
   would fix it and the first-input limit together.
7. none -> music in a browser that constructs the context suspended
   (iOS): until it runs, the song stays on the wall clock and switches
   at the next input without the 1.2 s lead-in. Chrome ran at once.
8. With sticky activation, music's `open()` makes the context at the
   first tick rather than the first note (in Chrome it runs at once).
