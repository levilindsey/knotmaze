Levi, 2026-10-13 (`docs/design/levi_notes_2026-10-13.md`), asked what
reduced motion should cover: "Not the intro animation or the
current-position-adjacent-segment-highlight-pulses, but it should cover

current-position-adjacent-segment-highlight-pulses, along with a dropdown
to change them. This could probably also help for high-contrast
accessibility. Maybe there could also be some high-level checkboxes for
setting high-contrast mode and reduced-motion mode, which then override

group near the top."

Two stages. Stage 1 is the panel and reduced motion. Stage 2 is the
pulse highlight modes. Stage 2 waits for K145 (a hover glow in the same
G2 paint files) to merge.

## Goal, stage 1

- **Reduced motion stills the maze's undulations** (the flow), on top of
  what it covers today. It does not still the intro animation or the
  pulses on the runs next to the player.
- **An "Accessibility" group near the top of the panel** with two master
  checkboxes, "Reduced motion" and "High contrast".
  - While on, each overrides every setting relevant to it. Off restores
    the viewer's own values: an override never overwrites a stored
    setting.
  - Both are viewer preferences like the Motion setting: they stay out
    of the link, are daily-exempt (K57), and are kept in localStorage.
    Storage failures must not break the page (see `motion.test.ts`).
  - "Reduced motion" and today's Motion setting must not fight. One
    control, or a checkbox that drives Motion, is your call.
- **High contrast, as far as it reaches today.** List every setting it
  should override: the background effect, the section colors, fog,
  thread casing and markers are candidates, and you may find others.
  Implement the ones that exist. Record the list and the values you
  chose in the handoff, so Levi can review them. The pulse highlight
  mode joins the list in stage 2.
- **The OS settings.** Say in the handoff how `prefers-reduced-motion`,
  `prefers-contrast: more` and `forced-colors` map onto the two
  checkboxes, and implement what is cheap.

### The OS settings

### A renderer finding (two parts)

1. In the asleep and paused branches, `flowRender(force)` calls
   `renderer.update()` BEFORE `fabricTick` assigns `renderer.fadeLength`,
   `flowStrength` and `flowSpeed`. A slider calls `wake()`, whose later
   frames redo the update; a toggle does not, so the one forced pass solved
   the crossing cuts and the flow with the OLD values (27k px off a fresh
   load, found by pixel-diffing a toggled page against a page loaded with
   the same setting). Fixed in `286b232`: `applyAccessibility` assigns the
   three fields itself. After it a toggled frame equals a fully re-updated
   one (extra `update()` passes change 0 px).
2. OLDER THAN K111, NOT FIXED (both off must be today's frames): a fresh
   STATIC page (`phy=0&fw=0`, or paused at load) draws its first frame with
   the crossing cuts solved at fade 0, for the same ordering reason (28k px
   off a refreshed frame). Real pages with physics on re-update while they
   settle, so it shows only for frozen scenes. A fix is to assign the three
   fields before the rest-branch `update()`; it would change today's
   frames, so it is Levi's call. Probes take a neutral refresh (Reduced
   motion on, then off) before a reference shot.
