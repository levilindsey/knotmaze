# K456: survive a lost WebGL context

Ledger: K456 (K470 was its duplicate and was dropped into it). One stage,
opus, 2 h cap.

## Goal

A lost WebGL context must not break the page. Phones drop contexts under
memory pressure and when the GPU process restarts. Nothing in `src/`
listens for `webglcontextlost` or `webglcontextrestored` today (only
`src/app/probe_hooks.ts` counts losses), so what a loss does is untested.

After this stage:
- the page keeps the player's state through a loss;
- it draws the same picture again after the restore, and play continues;
- a context that never comes back gets a visible message (or a reload
  that restores the attempt), not a silently frozen frame.

## Steps

1. **Measure today's behaviour on the desktop.** Use `WEBGL_lose_context`:
   call `loseContext()`, then `restoreContext()` after 0.5 s, and again
   with a 5 s wait.
   - Cases: the daily mid-solve (a bare link, after the intro), knot mode
     (`mf=0`), the thread reveal, fog, a burn race, confetti falling after
     a finish, and music auto plucks ringing.
   - Record per case:
     - whether the ticker survives;
     - whether Pixi restores its own resources;
     - which custom resources come back wrong or black: the G2/G3 data
       textures (`paint_model.ts`, `float_rows.ts`, `samp_table.ts`,
       `gap_mask.ts`, `junction_field.ts`), the background's
       RenderTexture, marker meshes, confetti;
     - whether input and the HUD still work.
   - Write the results to `.claude/probes/K456/results.md`.
2. **Pick the handling by correctness, not by size.** Candidates:
   - (a) let Pixi restore, and re-upload or rebuild every custom resource;
   - (b) on restore, rebuild the renderer and scene from the live state.
     The physics state lives in the worker or the PhysicsCore and survives,
     the URL is the design, and a daily's attempt is saved (K47).
   - (c) a reload that restores what it can, as the fallback when (a) or
     (b) cannot run.

   Explain the choice in a "Design" section of this doc.
3. **Build it.** Add Node tests where the logic is testable there. Add a
   probe in `.claude/probes/K456/` that forces a loss and a restore in
   each case from step 1, and checks:
   - the same pixels after the restore as before, as a same-state A/B
     (`phw=0` or `phy=0`, clocks pinned per `probes.md`);
   - a move after the restore lands;
   - no console errors;
   - a context that never returns shows the message or reloads.
4. **Phone check, if the phone is free.** Take the phone lock with
   `.claude/probes/agents/phone_lock_take.ps1` (K573 holds the phone until
   about 14:20) and run the probe's daily case on the Pixel. If the phone
   isn't free, say so; the check then goes to K156's next pass.

7. Music auto plucks keep sounding through the loss.

## Design

Choice: (a) let Pixi restore, and redo the one resource it cannot. Step 1
measured (a)'s premise directly: after a restore, Pixi and every custom
data texture are already pixel-exact (0 px); the only wrong pixels are
the background's RenderTexture, which no restore path refills, and a
frame that never gets drawn because the on-demand ticker is stopped. A
rebuild (b) would throw away a renderer that comes back right, cost a
scene build on the device least able to afford one, and risk the
renderer's retained state (lessons.md: never destroy textures that
retained state may still reference). A reload (c) stays only as the
player's own button when the context never returns: the attempt and the
preferences are saved at the loss, so a reload resumes the daily (K47).
No automatic reload, so a GPU that keeps failing cannot loop the page.

The handling (`src/app/context_loss.ts`, a pure state machine plus the
DOM overlay, wired in `main.ts`; the frame loop gains `suspend()` and
`resume()`):
- On `webglcontextlost` (Pixi's own listener already calls
  `preventDefault()`, which is what allows a restore): save the attempt
  and the preferences, hide the game clock as for a hidden tab, suspend
  the frame loop (stop the ticker; the idle poll and pushes do not
  restart it), drop held keys and refuse keys, the move pad and taps.
  Show a full-screen cover in the page's ink, so the white canvas never
  shows and pointer input never reaches the blind game.
- After about 3 s of visible lost time, the cover shows a message
  (graphics paused, progress saved) and a Reload button.
- On `webglcontextrestored` (it runs after Pixi's own restore): remove
  the cover, unhide the clock, resume the loop. The first frame after a
  resume re-renders the background's texture and draws, whatever the
  flags say.
- With no loss nothing changes: no listener runs, so every pixel stays
  as it is.

Hook K578 would share: the frame loop's restore redraw (the callbacks a
`resume()` runs before its forced frame). K578's cached still-maze
texture is a RenderTexture too, so it comes back empty and must
re-render there.

### What was built (bebdaa1, aaab8f2)

- `src/app/context_loss.ts`:
  - `ContextLossModel` is the pure state: lost or not, the lost time
    counted while the page is visible, and the message, due once after
    `MESSAGE_DELAY_MS` (3 s) of it.
  - `installContextLoss` adds the canvas listeners. A loss calls
    `preventDefault`, raises the cover, then runs `onLost`. A restore
    takes the cover down, then runs `onRestored`. Both handlers are
    wrapped in try/catch, and a 250 ms poll shows the message.
  - `createLossCover` makes `#km-gl-lost`, a fixed div in the canvas's
    ink at z-index 100 that takes every pointer. After 3 s it shows
    "Graphics paused", a line on what a reload keeps (aaab8f2, below)
    and a Reload button.
- `src/app/frame_loop.ts`:
  - `suspend()` stops the ticker. `ensureRunning` (pushes, the idle poll)
    will not restart it, and `onTick` returns at once.
  - `resume()` asks for a restore draw. The next tick re-renders the
    background's texture (once warmup wave 1 has drawn it), runs the
    `onRestore(fn)` hooks and renders, whatever the flags say.
  - `suspended` is a getter.
  - With no loss none of this runs.
- `src/app/input_keys.ts`: `keysLive()` is also false while the context is
  lost. `dropKeys()` releases held keys.
- `src/main.ts`:
  - On a loss: save the attempt and the preferences, hide the game clock,
    suspend the loop and drop keys. `visibilitychange` reads
    `document.hidden || glContextLost`, so a tab switch during a loss
    does not unhide the clock.
  - On a restore: unhide the clock and resume.
  - The Reload button calls `location.reload()`, and the saved attempt
    resumes (K47).
- `src/app/probe_hooks.ts`: `__knotContext()` returns `{lost, losses,
  restores, message, visibleMs, suspended}`.
- `test/app/context_loss.test.ts` has 12 tests:
  - the model: the delay, hidden time, a double loss or restore, the
    reset;
  - the installer: the order of its calls, the message shown once, the
    wait in a hidden tab, the restore, dispose, a handler that throws.
- aaab8f2: the message claimed "Your progress is saved." on every page,
  but only a daily's attempt in progress survives a reload (K47). The
  never case's reload of a free-play maze landed on the entrance. Now
  `createLossCover` takes a note read when the message shows: "Your
  progress is saved." while a daily attempt is live, "Reloading starts
  this maze over." in free play, and nothing in knot mode or on a
  finished daily. A 13th test covers the cover's text, the button and
  `hide`.

### What's left

- **Merge**, then Levi's look at three choices made here:
  - the ink cover hides the HUD and the panel for the whole loss;
  - the message waits 3 s;
  - there is no automatic reload, so a GPU that keeps failing cannot loop
    the page.
- **Residuals (known, not fixed):**
  - `KHR_parallel_shader_compile` is not re-enabled after a restore, so
    shader compiles after one may block. Inferred, not measured.
  - A WebGL init failure after Reload is not handled (as on master) and
    not tested.
  - Notes already scheduled on the audio clock ring out after a loss.
    New auto plucks stop, since the frame loop runs `autoAudioTick` and
    it ticks 0 times.
  - Focus left in a panel field is not handled: keys typed during a loss
    would still reach it (inferred). The cover takes the pointers, and
    the game's own keys are refused (measured).
  - The phone run had no `getevent` pickup watch. It was a 4-minute run
    under the phone lock.
  - Step 1's flake: master's never case died once with "Execution
    context was destroyed" before any loss. It is unexplained, and it
    did not recur in the never-case runs after it.
- **Seen, not K456's:**
  - `src/app/frame_loop.ts` line 307 (master has it too):
    `stepUnflagged = false;` sits after a `return`, so K6-1's
    observer flag never resets once set.
  - A reload of an `mf=0` link comes back in maze mode, because `mf` left
    the codec in K323 Stage A. A probe that reloads knot mode must pass
    `mf=0` again.
- **The hook K578 would share:** `loop.onRestore(fn)` in
  `src/app/frame_loop.ts`. The restore draw re-renders the background's
  texture, runs these callbacks, then renders. K578's cached still-maze
  RenderTexture also comes back empty after a restore, so it re-renders
  there.
