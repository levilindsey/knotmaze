# K76 brief: a thread-reveal exploration mode

Levi, 2026-10-12 (verbatim):

> "Also, similar to fog of war mode, I'd love to add another mode option.
> In this new mode, we don't render the threads of the maze until the
> player has reached an adjacent junction for them, and we then only show
> them for a certain distance away from the junction (a set distance, not
> a segment length ratio, and this distance should be a parameter). We
> should show a gradual fade-out to the end of the shown segment length
> (the fade-out distance should be another parameter). The part I'm not
> sure of yet, is that we need to somehow make it visually clear where all
> of the unvisited segment ends are, so the ends of these segments need to
> somehow look visually distinct at a glance. Maybe a background
> highlight. Maybe an in-thread highlight near the end (in which case,
> we'd actually need to handle the fade-out differently, I guess). And in
> this mode, with cameraMode set to fit, we'd only pan/zoom to fit the
> current explored segments and the visible bits of the adjacent
> segments."

## Stage 1 (this agent): design and prototypes, no merge

1. **Mechanism.** Find the right engine and write it down.
   - The likely fit is the appearance reveal, which since G2.1 runs per
     pixel. It already hides threads, gates crossings until both passes
     show, and fades. A gameplay-driven reveal would set each chain's
     visible intervals to the traveled runs, plus `revealDistance`
     along every arm of each visited junction, with a `revealFade` ramp.
   - Gaps: a hidden over thread must not cut a gap into a visible under
     thread. Work out how the G1 casing masks and the gate show times
     handle that.
   - Also cover junction webs, markers, the yarn (`pv=string`), pulses,
     hover and hit-testing: are hidden runs tappable? They shouldn't be.
   - Cover how the mode relates to fog of war: exclusive, or composable?
2. **The unvisited-end look**, Levi's open question. Prototype at least:
   - a background halo behind each frontier end;
   - an in-thread highlight near the end, with its own fade design;
   - a cap or bead at the frontier.

   Add anything better you find. Render each on the same frozen state
   (`.claude/probes/probe_winbanner.mjs` clicks a route; pin
   `renderer.paintClock`) at desktop and phone sizes, as a contact sheet
   Levi can choose from.
3. **Camera.** With `cameraMode` fit, frame the explored runs plus the
   visible bits of the adjacent arms. Fog of war's fit-to-visible-region
   path is the precedent.
4. **Params.** A mode switch, `revealDistance` and `revealFade`, with
   names, ranges, defaults and panel placement.
   - They must be APPENDED to the current codec table, with defaults that
     leave today's links unchanged (mode off).
   - K73 is adding codec v4 right now, so the implementation stage
     appends to v4.
   - The mode is not a daily playback preference, so turning it on leaves
     the daily, unless Levi wants dailies with it (ask).
5. **Cost.** Estimate per-frame GPU and CPU, and give a phone-gate plan.

## Deliverable

`docs/design/K76_reveal_mode.md`, with the contact sheet in
`.claude/probes/K76/`. Put first the recommendation and the decisions
for Levi: the end-marker look, the param names and defaults, and the
fog-of-war relationship. Prototype code stays on the worktree branch;
the implementation is stage 2, after K73 and K75 merge.

## Constraints

- Use a private vite cacheDir for the worktree's server, and leave 5173

### Calls made in this stage

- The whole-chain flag lives in KPAINT texel `chain` .x, not in KGEOM as
  section 7 says. KGEOM's G0 is full, and G0.w is the paint flag.
- VIS is not a PAINT_ITEM: `glslConstBlock` would emit a PI_ constant into
  master's program text.
- A VIS item sets no chain's paint flag (`writePaintItems` keeps a
  `painted` array), and a whole chain gets no VIS item.
- The explore program is a separate Shader on the same resources, so with
  the mode off every ribbon binds master's program. `bindGap` binds the
  explore program's uGapData too.
- The looks are GPU-only, like K111's modes. `kExploreAt` mirrors the
  visibility, not the looks.
- The probe-only model keeps the prototype's derivation from the
  controller's sets and resets on `c.restarts`. Its flaws are listed
  under stage 2c below.
