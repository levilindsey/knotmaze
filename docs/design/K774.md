the beat rider and the hunter (`clk=beat`, `mt=hunter`), a catch never
lands. The model counts it and respawns both, but nothing follows: no HUD
count, toast, heart or banner. Evidence (read-only; copy what you need

### The inference: HELD (the code and the unit test; the page is next)

- `test/app/beat_catch.test.ts` drives the real beat frame (fake clock,
  2 ticks a 60 Hz frame) with main.ts's catch path mirrored. Old flow,
  every first catch with `t = 1` among seeds 1-40: the catch is counted
  (`catches` 1, HUD 0), the next departure snaps the catching move
  short of 1, the controller takes phantom moves, the minotaur rejects,
  and after 600 more frames it has still not landed.
- Fixed flow, seeds 1-24 played out: 253 catches, 168 of them (66%)
  landed inside a departure's commit, the path the old flow lost (the
  rest landed in tickTurnMino as before). The old flow breaks the game
  at its first `t = 1` catch.

- The catch move R defers with `t = 1` (an arrival contact). The frame
  that reaches R's arrival tick runs `advance` BEFORE any progress: the
  next departure commits in the same call, `moveAlong` -> `fc.tapEdge`
  accepts it (the controller was never respawned, so it is a phantom move
  from the catch junction), `tm.turn` returns "reject" (its player is at
  the start), and `beginMove` snaps R. The new progress is about 0, so
  `tickTurnMino` never sees `frac >= 1`; the last frame before the
  arrival reached only 0.95-0.99 (K767's per-run maxima).
- It never lands later either: the rider never rests (the Lead order
  always has "back"), and the head check never fires (`fc.head` follows
  the phantom moves, so it equals `r.ahead`). Meanwhile every later
  `tm.turn` rejects, so the minotaur stops taking turns (K767: turns
  stuck at 7).
- Also exposed: a contact at `t < 1` that falls between the last frame's
  progress and the arrival is missed the same way.

### The fix (implemented 08:00; type-checks, the beat tests pass)

- (a) `moveAlong`, after its walker and beat guards: a pending catch of
  this minotaur lands first (`setMoveProgress(t)` to put the dot at the
  contact, then `turnCaught(wait, true)`), and the move is refused.
- (b) `BeatRider`: a `restAt` from inside a commit ends the advance (a
  rest counter), so the rider does not try the old junction's other arms
  on the respawned controller. Without it the fixed flow failed: after
  an in-commit landing the rider tried the next arm and the entrance's
  tail was accepted from the respawned start. It also fixes a latent
  case: the fallback `turnCaught` (no `lastContact`) inside a commit
  returned true and the rider rode on past the rest.
- (c) `turnCaught`'s respawn path rests the rider at the new head (the
  restart path already does, through `restartSolve` -> `beat.reset()`).
- `beat_frame.ts`'s header no longer claims a catch is refused on the
  next junction.
- The turn clock never reaches (a) with a catch pending: a tap mid-move
  is ignored or waits for the arrival, keys act at the arrival after
  tickTurnMino has landed the catch, `carryStep` waits for the dot, and
  `useTool` refuses while a catch is pending.
