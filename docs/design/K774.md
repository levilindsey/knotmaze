### The cause: the inference held (unit test and page)

- The catch path (file:line at 3abeabb6). `turnAfterMove`
  (`main.ts:2414`) calls `tm.turn(eid)`. On "caught" the model has
  already counted the catch (`catches++`) and moved ITS player to the
  entrance, and `deferCatch` (`main.ts:2445`) parks the catch as
  `pendingCatch = {tm, t: tm.lastContact.t, wait}` (`main.ts:2448`). The
  controller (`fc`) is not respawned yet, and the HUD subtracts a pending
  catch from `tm.catches` (`main.ts:1361`). The catch landed in one place
  only: `tickTurnMino` (`main.ts:2563`), once the move animation's
  `moveProgress` reached `t` (`main.ts:2576`). There `turnCaught`
  (`main.ts:2304`) respawns, shows the HUD count and the toast, takes a
  heart, or restarts when the hearts run out.
- On the beat, `beat_frame.tick` runs the rider's `advance` before any
  progress, and `BeatRider.advance` (`beat_rider.ts:109`) commits the
  next departure from a junction in the same call that reaches it. So the
  frame that reaches the catching run's arrival tick first calls
  `moveAlong` for the next run:
  - `fc.tapEdge` accepts it: a phantom move from the catch junction,
    since the controller was never respawned;
  - `tm.turn` rejects it, since its player is at the entrance;
  - `beginMove` snaps the catching move (`anim = null`).
- With an arrival contact (`t` = 1), the last frame before the arrival
  reached only 0.95-0.99 (K767's per-run maxima), so `frac >= 1` never
  happened.
- It never landed later either. The rider never rests, since the Lead
  order always ends with "back". The head check never fires, since
  `fc.head` follows the phantom moves. Every later `tm.turn` rejects, so
  the minotaur stops taking turns (K767: turns stuck at 7).
- A contact at `t < 1` that falls between the last frame's progress and
  the arrival was lost the same way.

### The fix (`9fbcef97`)

- (a) `moveAlong` (`src/main.ts`, after its walker and beat guards): a
  pending catch of this minotaur lands before any next move. The dot is
  set at the contact (`setMoveProgress(t)`), then `turnCaught(wait,
  true)` runs, and the move is refused. `pendingCatch` is cleared first,
  so `tickTurnMino` cannot land it a second time.
- (b) `BeatRider` (`src/game/beat_rider.ts`): `restAt` bumps a private
  `rests` counter, and `advance` returns as soon as a commit rested the
  rider. So it does not try the old junction's other arms on the
  respawned controller.
  - Without it the fixed flow failed. After an in-commit landing, the
    rider tried the next arm, and the controller accepted the entrance's
    tail from the respawned start.
  - It also ends a latent case: the fallback `turnCaught` (no
    `lastContact`) inside a commit returned true, and the rider rode on
    past its rest.
- (c) `turnCaught`'s respawn path rests the rider at the new head
  (`beat?.rider()?.restAt(fc.head)`, a no-op off the beat). The
  out-of-hearts path already rested it, through `restartSolve` and
  `beat.reset()`.
- `src/app/beat_frame.ts`'s header now says where a catch lands.
- The turn clock never reaches (a) with a catch pending:
  - a tap mid-move is ignored, or waits for the arrival;
  - keys act at the arrival, after `tickTurnMino` has landed the catch;
  - `carryStep` waits for the dot;
  - `useTool` refuses while a catch is pending.

### The other paths

- **The walker** (K114's other clock) cannot meet the pattern. The cut,
  and with it the walker's lead and delay modes (`fabric_controller.ts:947`),
  applies only to the classic game off the beat (`url_state.ts:1218`:
  `cut: gameMode === "classic" && clock !== "beat"`). So a walker game
  has no minotaur and no catch.
- **The sprint** is covered by (a). A sprinted move's catch takes the
  same `turnAfterMove` -> `deferCatch` path; the skip only changes the
  minotaur's turn. The `spr=on` run's catches came well after the sprint
  was spent; the phone probe's desk dry run (below) caught the rider just
  after the sprint's skipped turn, and that catch landed too.
- **Lives** are covered. A catch takes a heart in `turnCaught`. The catch
  that takes the last heart restarts the solve with every heart back
  (`restartSolve(true)`), shown by the toast "Out of hearts! Starting
  over.".
  - There is NO banner when the lives run out, by design
    (`.claude/rules/gameplay-minotaur.md:584-598`, `src/game/lives.ts:43`).
    The win banner shows "hearts L / N" only at a finish. So the brief's
    "the banner when the lives run out" has nothing to land.
  - That lore entry says lives were "Not checked on a page yet". The
    lives run above is that check, on the beat clock.
