# K173: split the rules lore so an agent loads only its area

Approved by Levi, 2026-10-14 about 07:53: "Splitting the rules files
seems worthwhile." One stage, for one agent (opus, in a worktree).
Ledger: K173.

## Why

Claude Code attaches a `.claude/rules/*.md` file to a session when the
session reads (or edits) a file that matches the rules file's `paths:`
list. Knotmaze's lore lives in seven such files, 185 KB in all (about
46k tokens):

| file | bytes | lines | paths |
|---|---|---|---|
| render.md | 61,664 | 930 | `src/render/**`, `test/render/**` |
| gameplay.md | 35,760 | 547 | `src/game/**`, `src/ui/**`, `src/audio/**`, `src/main.ts`, `test/game/**`, `test/ui/**`, `test/audio/**` |
| physics.md | 33,641 | 526 | `src/physics/**`, `test/physics/**`, `test/*.regression.test.ts`, `test/sweep.manual.test.ts` |
| probes.md | 26,244 | 423 | `scripts/**`, `.claude/probes/**` |
| render-gaps.md | 14,522 | 221 | `src/render/gap_mask.ts`, `src/render/ribbon_renderer.ts`, `src/render/ribbon_mesh.ts` |
| generation.md | 8,920 | 142 | `src/core/**`, `src/geometry/**`, `test/core/**`, `test/geometry/**` |
| notices.md | 4,383 | 71 | `notices/**`, `test/notices/**`, `vite.config.ts` |

One read of `src/main.ts` brings all 36 KB of gameplay lore, one read of
any render file all 62 KB of render lore, and an agent that touches
render, gameplay and one probe carries about 31k tokens of lore before
it starts. What it cost (LEDGER K173): K140's first compaction came 9
minutes in, from rules attachments (82 records, 1.12M characters); K156
3c and K154+K169 (Sonnet) reached 205k and 298k of context within 12
minutes; K180 (Opus) compacted 9 times in its first 44 minutes; on
2026-10-14 the three Opus agents started at 07:38 compacted 2 to 4 times
in their first 17 minutes. 82 records for seven files means a file
attaches more than once (again after each compaction? on every matching
read?): find out which.

## Goal

An agent pays only for the lore of the files it works on and loses
nothing it needs: each passage still attaches whenever an agent reads a
file the passage is about. Every passage is kept verbatim, only moved.

## The stage

1. **Before: measure attachment from the records.** This repo's agent
   transcripts are under
   `~/.claude/projects/C--Users-lsl-Repositories-knotmaze/<session>/subagents/`
   (most in session `d8031183-cd9e-4b70-9968-661d70634c84`); find each
   agent by its first user message ("You are the K140 agent ..."). For
   K140, K156 3c, K154+K169, K180, K148+K149, K120 and K90 stage 1a,
   record: which rules files attached, when, and what triggered each
   (which read; whether a file attaches again after a compaction or on
   every matching read); the characters attached in all; and which
   files each agent read (its Read and Edit calls). Also how a worktree
   path matches: agents work in `.claude/worktrees/<id>/`; does the
   worktree's own `.claude/rules/` attach, matched relative to the
   worktree root? Keep the scripts and numbers in `.claude/probes/K173/`
   and the summary in this doc. This is the "before".
2. **Design the split.** Map each passage (a `##` section, or a lore
   block such as `PROBE LORE (2026-10-12, K56): ...`, or a bullet) to the
   files it is about: the source files, functions and identifiers it
   names (check with Grep). Group passages by the files they cover, so a
   rules file's `paths:` lists exactly the files its passages are about.
   Narrow paths matter more than file count; a small file is fine. A
   passage about many areas (a general probe rule, the determinism
   rules) may stay in a broad file, but keep broad files small.
   `src/main.ts` touches every feature: decide what a read of it must
   bring (perhaps the passages about main.ts itself plus a short index
   of where each subsystem's lore lives). Each new file gets a short
   header like today's (what it holds, where the rest went) and the same
   frontmatter format. Name files `<area>-<topic>.md` (for example
   `render-paint.md`, `gameplay-daily.md`, `probes-phone.md`); keep a
   plain `<area>.md` only for an area's general lore.
3. **Build it as a script, not a hand edit.** The three agents running
   now (K90 stage 1b, K132, K100) merge before this one and edit
   `gameplay.md`, `generation.md`, `probes.md`, `render.md` and
   `physics.md` (K132 rewrites passages), so the split has to be redone
   on the merged files. Write a tracked `scripts/split_rules.mjs` (node,
   no dependencies) and a manifest (`scripts/split_rules.json`) that
   assigns each passage, by a stable anchor (its heading, or the first
   words of its first line), to an output file. The script reads the
   current rules files, writes the new ones and deletes the old ones. It
   fails loudly on a passage the manifest does not assign and on an
   anchor that matches nothing or more than once, and it proves the
   result: every line of every old file appears in exactly one new file,
   verbatim, and nothing is added except the new headers and
   frontmatter. Ideally it also applies the pointer rewrites of step 4
   from a map, so the whole change is one command on any later master.
4. **Update the pointers.** CLAUDE.md's "Lore and history" section
   (keep it short: CLAUDE.md must not grow; a full index can live in a
   doc that is not auto-loaded, such as `docs/lore_index.md`, never in a
   rules file without `paths:`, which loads in every session),
   cross-references inside the rules files ("`gameplay.md`'s THE HEAD"),
   `docs/design/*.md`, `docs/history.md`'s bracketed notes, and comments
   in src/, test/ and scripts/ that name a rules file. LEDGER.md is the
   coordinator's: list its references (line, old, new) in your report.
5. **After: measure.** (a) For every tracked file under `src/`, `test/`,
   `scripts/` and `notices/`, plus `vite.config.ts`: the bytes of rules
   a read of it attaches, before and after (median, 90th percentile,
   max, and the hot files `src/main.ts`,
   `src/render/fabric_maze_renderer.ts`,
   `src/physics/particle_system.ts`, `src/ui/tweakpane_panel.ts` and
   `scripts/phone_pass/*.mjs`). (b) The read sets of the agents from
   step 1, replayed against the old and the new `paths:` (the bytes
   attached per agent, once per file). Put both in a table here.
6. **Check one real attachment.** At most two headless runs of
   `claude -p --model haiku` in your worktree, each reading one file
   whose lore moved to a narrow glob; then find that run's transcript
   and confirm which rules files attached. If a glob does not match as
   expected, fix the paths and say so. If step 1's records already
   settle how paths match, one run is enough; if `claude` will not run
   headless here, skip this and say so.

## Working rules

- PowerShell for commands (Windows).
- Do not open files under `src/`, `test/`, `scripts/`, `notices/` or
  `.claude/probes/` with the Read tool: each read attaches the lore you
  are moving (up to 62 KB). Check source with Grep, or a shell read of a
  few lines. The rules files themselves attach nothing: read them
  directly, one at a time, and commit the manifest as you go, so a
  compaction loses nothing.
- Never open a transcript with the Read tool (they run to megabytes):
  parse them with a script.
- No app code changes, so no test suite and no perf lock: the merge runs
  the suite.
- Commit work in progress at every milestone, broken or not; never push.
  Do not edit LEDGER.md.

## Stop rule

Run `Get-Date` at the start and at each milestone. Stop when the stage
is done or after 2 hours of wall-clock time, whichever comes first. A
compaction is not a stop: after one, re-read this brief and `git log`,
then go on. Before the handoff, `git fetch`: if `origin/master` changed a
rules file since your branch point (the batch above merged), redo the
split on it (rebase, take master's old rules files, rerun the script,
fix the manifest for new or changed passages) and commit. Then append a
"Stage 1 handoff" section to this file: what was done, the before and
after numbers, the exact recipe to redo the split on a newer master,
and what is open. Commit, and report. The report ends with a
`Ledger items` list (follow-ups, residuals, decisions for Levi, the
LEDGER.md references to rewrite) and the K173 handle fields (branch,
last commit, evidence, next).
