## The work

1. **Check the mid-move hypothesis first.** The controller may commit a
   move at once and let the dot animate after. If so, a tap made while
   the dot is still moving resolves against the destination's choices,
   and the stretch of the arrival run the dot has not covered yet counts
   as a backtrack. Probe it: tap mid-move on that stretch, and near the
   destination's outgoing runs, and log which run each tap takes. Report
   what you find.
   - If it is confirmed, a backtrack mid-move should take only the
     stretch the dot has already covered. The stretch still ahead of it
     is empty space for taps, so an outgoing run in reach can win there.
2. **The preference.** The arrival run wins only when it is clearly
   nearer: about 1.5x nearer than the nearest outgoing run. Tune the
   factor with a tap census (item 4). A tap whose only run in reach is
   the arrival run still takes it, so a tap well along that run is still
   a backtrack. No arrival run (before the first move) means no bias.
   Under the fire, burnt runs stay out (`choices()` drops them).
3. **One rule.** Put the choice in a small pure function (the per-run
   distances plus which run is the arrival run in, the run out), with
   unit tests: the bias, the arrival run alone in reach, no arrival run,
   a self-loop arrival run, mid-move. The hover must light what a tap
   takes, so both go through it. Arrow keys and the move pad are out of
   scope.
4. **The census.** Synthetic taps on a grid around each junction of a
   few seeds, at the phone viewport (411x753 @2.625, touch radius) and at
   1400x900 (mouse radius), after a move into each junction. Count where
   the taps go, before and after:
   - a tap inside exactly one run's drawn ribbon must still take that
     run, the arrival run included;
   - the taps that land where the arms overlap, or in the margin between
     them, should now go to the outgoing runs.
   Report the counts and the factor you chose.
5. **Verify.** A few screenshots of the hover near a junction, before
   and after. The full suite and `npm run build` pass.
6. **Lore.** A TAP PREFERENCE entry after PICK MARGINS in
   `gameplay-camera.md`. Mention the mid-move finding there too.

### Mid-move (item 1): confirmed

On the pristine build moveAlong commits the move at once, so while the dot
travels run R into junction J the controller's head is J and `choices()`
holds R in full. With the dot frozen at 30% of R (k111's first move, 32
ctrl), `edgeAt` on 19 points along R's centerline returned R at all 19,
and a real click at 70% showed the pointer cursor, queued and, on arrival,
walked back. Now (same frozen state): R at 5 of the 6 covered points, 247
(an outgoing run whose ribbon the arrival run crosses) at the sixth, 0.20,
and nothing at the 13 uncovered ones; a real click at 70% leaves the head
put. Outgoing runs at 2 and 4 ctrl from J take their own taps.

### Census (item 4): factor 1.5

Three mazes (k111, 1471kin, maze7; 178-181 junctions each), every junction
entered on each run, a 0.04 world grid over a 3.2 world disc, mouse

mouse 46.8-47.1% to 35.7-36.2%, touch 43.0-43.1% to 33.3-33.5% (k111:
24,490 of 233,001 mouse taps and 88,147 of 924,158 touch taps moved to the
outgoing run, none the other way). Inside both ribbons: 41.9% to 28.7%.

the distance past the edge. Factors on k111 mouse: 1.25 leaves 38.7%, 2
leaves 33.2% (touch 29.4%) at 1.4x the loss. The live `edgeAt` agreed with
the offline classes at 1 point in 61: 0 mismatches in about 180k
