### 1. The rule kit

`src/game/rule_search.ts`: pure walk-graph code, engine-exact (K108:
+ - * /, `Math.sqrt` and the integer helpers; no `Math.hypot`, trig or
`**`). The game and the search share one judge.

```ts
// One tap's move under a rule: the runs it walks (one, or a slide), the
// vertex it ends at, the rule state after it, and its length.
interface RuleMove { runs: number[]; to: string; state: number; length: number }
interface WalkRule {
  readonly states: number; // the rule's states, 0 .. states - 1
  readonly start: number;  // the state when the solve starts
  // The move a tap on `run` from `from` makes in `state`; null: refused.
  step(from: string, run: number, state: number): RuleMove | null;
}
function ruleSearch(
  walk: WalkGraph,
  rule: WalkRule,
  from?: { vertex: string; state: number }
): { solvable: boolean; fewest: number; shortest: number; route: number[] };
function composeRules(...rules: WalkRule[]): WalkRule; // one expander at most
```

- `ruleSearch` is a BFS over (vertex, state) for the fewest taps to the
  exit, and a Dijkstra for the shortest length, plus one best route by
  taps. A backtrack is not a move in the search: it returns to a node
  already reached, so it never shortens a route.
- `composeRules`: at most one rule expands a tap into several runs
  (ice). The others judge each run of the move in order, each threading
  its own state. One refusal refuses the whole tap. The composed state
  is the product of the parts' states.
- The controller calls the same `step` in `tapEdge`.
- Placement: each mechanism draws from its own `SeededRNG`
  (`util/random.ts`), seeded from the design seed and the mechanism's
  name. Never the shared `rng()`: its draws build the maze. Draw, search,
  and redraw up to 32 times until the search says solvable and the rule
  bites (the best legal route by taps differs from the plain one). Keep
  the first draw that does both. Failing that, keep the last solvable
  draw. Failing that, place nothing, and the HUD row says the rule found
  no layout for this maze.
- Par: with a rule on, F is the kit's fewest taps from the start, and
  P = `parFor(F, parSlack)`. Strict mode asks the kit from the head's
  (vertex, state) after each move, in place of `runsToExit`.
- Strokes count actions under a rule. Today `strokes` is `taps.length`,
  one per run walked. With ice a tap can walk several runs, so a stroke
  is one entry of `actions` (one per tap, a backtrack included).
- Stars: R = walked / the kit's shortest length. The plain optimum can be
  illegal under a rule.

### 2. Ice runs (4.19)

- Param `ice` (`ice`): the share of the core runs that are icy, [0, 0.5]
  step 0.05, default 0.
- A tap on an icy run walks it, then carries on straight through its far
  junction, along the same strand, into the next run. It keeps going
  while the runs are icy. The slide stops at the far end of the first run
  that is not icy.
- The slide also stops where the strand does not go on (the walker map's
  `cont` is -1), at an END, at the exit, and before a run this slide has
  already walked. No slide loops.
- "Straight on" is the strand's continuation: `cont` in `walker.ts`. It
  is topological (chain and control index), so it is engine-exact. There
  is no heading test.
- The walker map needs the tangle graph (`walkerMapOf(scene.tangle,
  walk)`, as main.ts builds it for K114's walker). Build the layout where
  the scene is built and hand it to the controller with the rules.
- One tap is one stroke, however many runs it slides.
- The slide uses the cut's carry queue. The controller puts the rest of
  the slide in `carry`, as `logMove` does for a contracted move, and
  main.ts `carryStep` walks `carry[0]` on each arrival. Today
  `carryStep` returns at once unless `fc.cutOn`: widen that gate to "the
  cut is on, or a carry is pending". `replayActions` then rebuilds a
  slide as it rebuilds a contracted move, so Undo works unchanged.
- A backtrack after a slide (a tap on its last run) undoes the whole
  slide. It walks the slide's runs back in reverse, as one action, to the
  junction where the slide began. Sliding back by the rule could
  overshoot that junction.
- The look: icy runs take a pale frost color. Override the icy runs'
  colors in the run table that `recolorScene` hands the renderer
  (`src/app/scene.ts`, `buildSectionRuns` in `section_colors.ts`), after
  the build. No new GL program. Section 4's glitter is out of scope.
- HUD: a row while ice is on (for example "ice · slides carry you
  straight on"). Share: the title line names the rule in words. Section 4
  asks for no new stat.

### 3. The color rule (4.18)

- Param `colorRule` (`cru`): off | alternate | cycle, default off.
- alternate: every run is light or dark. Never walk two runs of one
  shade in a row.
- cycle: every run is one of three colors, walked in order (first,
  second, third, first, and so on). The first run may be any color.
- Section 4 also offers "never the same color twice in a row". With three
  colors that refuses about one arm in three, and only where two runs at
  a junction share a color. alternate bites harder and reads better, so
  it replaces that form.
- The rule's state is the last color walked, with "none" at the start. A
  backtrack is always allowed and restores the state from before the
  move it undoes.
- Icy runs carry no color: the rule skips them. A slide that would end on
  a run of the wrong color is refused before it starts.
- A refused run does not pulse: `choices()` leaves it out, as it leaves
  out broken runs. A tap on one still says why: a toast at most once per
  1.5 s, as the smolder toast does, and the cut's dull pluck (main.ts
  `cutPluck` at `REFUSE_OCTAVE`). Do not touch `src/audio/`.
- Placement colors every run from the mechanism's stream, then plants one
  legal route: a seeded detour from the start to the exit (not the plain
  shortest route), recolored to obey the rule. Every draw is then
  solvable. The kit checks that the rule bites.
- The look: while the rule is on, its colors replace the color scheme's
  on every maze run, through the same run-table override as the frost.
  Make each run flat (one color end to end, no ramps), so the junction
  blend cannot hide which run is which. alternate is lightness alone: a
  light and a dark shade of the maze's hue. cycle's three colors sit far
  apart in lightness as well as hue.
- Colorblind play: under cycle, each run leaving the head wears a small
  glyph for its color (circle, triangle, square), through
  `marker_glyphs.ts` and `marker_mesh.ts`.
- HUD: a row with the color the next run must have (cycle) or the shade
  it must not have (alternate). Share: the title line names the rule in
  words.

## Design (the stage 1 agent, 2026-10-21, step 1)

- THE KIT (`rule_search.ts`). `WalkRule` as above plus an optional
  `expands` flag (ice sets it). `plainRule(walk)`: any incident run, to its
  far end, one state. `ruleSearch` numbers the nodes `vertexIndex x states
  + state` (vertices in `walk.vertices` order), runs a BFS for the fewest
  taps (incident runs in `vertex.edges` order, so the route is
  deterministic) and a binary-heap Dijkstra for the shortest length (ties
  by node number). Any state at the exit is solved. `route` lists the
  tapped runs; `routeRuns` every run walked. `composeRules`: the expander
  (or the first rule) proposes the move; every other rule judges each of
  its runs in order from the vertex that run leaves, threading its own
  state; one refusal refuses the tap; state = mixed-radix product.
  `bites(walk, rule)`: the legal search's fewest, shortest or walked runs
  differ from `plainRule`'s.
- PLACEMENT (`placeRule` in the kit): `ruleRng(seed, name)` is a
  `SeededRNG` on FNV-1a of `<seed>:<name>` (Math.imul only). Up to 32
  draws from that one stream: first solvable and biting draw, else the
  last solvable, else none (`placed: false`, the HUD says so). EXEMPT
  runs (never icy, no color): title runs and every run touching `start`,
  `mazeStart` or the exit (the cut's `cuttable` set, inverted). Core runs
  = the rest.
- ICE (`ice.ts`). A tap from v on run r is the directed run `d = 2r` when
  `e.va === v`, else `2r + 1`; the slide's next run is `cont[d ^ 1]`
  (the run end at the arrival). Stops as the brief lists. Placement: k =
  round(share x core) runs by a partial Fisher-Yates.
- THE COLOR RULE (`color_rule.ts`). Colors per run (`Int8Array`, -1 none:
  exempt and icy runs). State = last color + 1 (0 none): alternate 3
  states, cycle 4. Placement: a color per core run from the stream, then a
  detour: a random junction W, a randomized BFS start -> W, then W -> exit
  avoiding the first leg's vertices (8 tries, else the plain BFS route),
  its colored runs recolored in walk order to obey the rule. Under ice the
  search with the composed rule decides (a slide can carry off the
  detour), and the icy set is placed first, from its own stream.
- CONTROLLER. `setRules` keeps `rule` (null unless ice or the color rule is
  on, collapse, fragile, the cut and the fire are off, and the walk has a
  layout). New state: `ruleState`, and per forward move `moveStarts` (the
  path length before it) and `stateStack` (the state before it). A fresh
  advance asks `rule.step`; null returns the new result `"refused"` and
  changes nothing (`replay` and `replayActions` treat it as a failure);
  otherwise the state moves on and `carry` takes the rest of the slide. A
  fresh backtrack (the path's top run) pops the whole move: the state
  comes back, `carry` takes the move's other runs in reverse, each the
  path's top in turn. Strokes = `actions.length` under a rule; `choices()`
  drops runs the rule refuses (the backtrack run stays);
  `refusedChoices()` lists them for main's toast. Par's F and strict's
  runs-left come from the kit (strict judges only once the carry is
  empty); `optimal` (the kit's shortest) feeds the stars and the
  efficiency. With no rule every path is the old one.
- MAIN. `carryStep`'s gate: the cut is on, or a carry is pending. Undo
  uses `replayActions` when the cut or a rule is on. A tap that picks no
  choice checks the refused runs in reach (`runsInReach` over
  `refusedChoices()`): toast + `cutPluck(eid, REFUSE_OCTAVE,
  REFUSE_STRENGTH)`, throttled 1.5 s.
- LOOKS. `ruleRunTable` (section_colors.ts) rebuilds a per-run table
  shaped like the segments scheme's (one flat RGB record per walk run, the
  scheme's own records left for exempt runs where it has them) and paints
  frost on icy runs and the rule colors on colored ones. scene.ts applies
  it at the build and in `recolorScene`.
