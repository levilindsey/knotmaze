## The question

On the broken build (`f18dd07^`), with the split on through capability,
why does the frame draw no crossing gaps, while `setGapSplit` on the
same build draws them?

## Hypotheses to test (not findings)

  causes: the pre-pass is armed only by `setGapSplit`, or `contextChange`

  offset in the shipped mask; a larger one would read as "no gaps").

### Root cause: the mask was sized in CSS pixels, the paint reads device pixels

- `ensureMaskSize(renderer.width, renderer.height)` made the mask
  `renderer.width x height` at resolution 1, and `uGapSize` the same.
  In Pixi v8 `renderer.width` is CSS px: 1600x900 for a 1600x900 page.
  The header said "1:1 device pixels with the canvas (renderer.width x
  height)", which holds only at dsf 1.
- GAP_MASK_FRAG indexes the mask by `gl_FragCoord`, which counts the
  canvas's DEVICE pixels: 2400x1350 at dsf 1.5.
- So at dsf 1.5 each fragment read the texel for 1.5x its own position.
  That texel was owned by another chain or by no ribbon, or lay past
  the mask's edge, and both read keep 1.0. The split drew almost no
  gaps.
- At dsf 1 the two sizes coincide, and the split draws its gaps.
- The mask's own contents were right. Read back at dsf 1.5, it held its
  gaps, drawn in CSS px: 57,542 cut texels, against 57,538 at dsf 1.
  The frame's cut (the pixels that change when the mask's debug tint is
  turned on) fell from 56,491 px at dsf 1 to 3,982 at dsf 1.5 (b10q and
  b15q below).

### Why the two enabling paths looked different: dsf, not the path

- On the broken build (`cfc79bd`), the capability path and
  `setGapSplit(true)` draw the same frame: `load~S` is 0 px at both dsf
  1 and dsf 1.5.
- Every K320 stage-2 and K550 probe set `deviceScaleFactor: 1`. That is
  all 14 scripts in the main checkout's `.claude/probes/K320/` that set
  a viewport.
- K551's `gaps_check.mjs` and Levi's desktop run at dsf 1.5.
- The hypotheses:
  - **(a) is false.** The pass rendered hundreds of times under the
    capability path (b15q: 403 renders by the end of the load capture).
  - **(b) is not the cause.** The warm-up linked `section-rgb-gap` in
    wave 1, and S matched load to the pixel.
  - **(c) is not the cause.** The framebuffer check passed, and the mask
    read back with its gaps (bad texels 0).
  - **(d) is the cause,** but as a size mismatch, not a stale view or
    offset.

### The fix

The fix is `72dfd30` plus `2b9d5f2`, in `src/render/gap_prepass.ts`
only. No shader text changed, so nothing compiles cold.

- **`ensureGapMaskSize(cssW, cssH, resolution)`** sizes the target to
  the canvas's device pixels, at the renderer's resolution. It uses
  `gapMaskPixelSize`, which rounds as Pixi does.
  - The frame stays in CSS px. Pixi's viewport is the frame times the
    resolution, so the camera's CSS-unit transform fills the whole
    target.
  - `uGapSize` is the pixel size.
- **`fitGapTarget(rt, pw, ph, res)`** is the one sizing rule for any
  target the paint indexes by `gl_FragCoord`, exported for K550's
  under and deep masks. It calls `rt.update()`, because Pixi refreshes
  the frame only when the pixel size changes.
- **The dirty rule gains `canvasRes`.** A dpr change at the same CSS
  size resizes the target, which drops its contents, so the pass must
  re-render.
- **The split stays dark by default** (`f18dd07` untouched). On master
  + fix, a load runs 0 pre-pass renders, and load~C is 0 px.
- **Every enabling path draws the gaps at dsf 1.5,** at the brief's link
  and at `?1.5`:
  - `setGapSplit` (h15q; f15, h15);
  - the default flipped on (variant B: vb15q, vB15);
  - the capability path restored (variant C: c15q, c15).
- **A batch line without its own link** (`port subdir label dsf`) now
  loads the probe's default, the brief's link, not `?<dsf>`:
  `run_batch.ps1` passes extra fields only when the line has them.
