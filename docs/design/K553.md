# K553 brief: why K320's gap split drew no crossing gaps when capability turned it on

Ledger item K553. A diagnosis stage: one Opus agent, two-hour cap.

## Where things stand (master)

- **K320** splits the combined section-rgb program so the paint compiles
  faster cold. In stage 2b the paint samples a gap mask that a pre-pass
  renders:
  - cold paint is 29,414 chars / 1,735 ms vs 46,361 / 3,217 ms (D3D11
    medians);
  - design: `docs/design/K320_section_rgb.md`; stage 2 brief:
    `docs/design/K320_stage2.md`;
  - the commits are `ffd3864` (2a, the data plane) and `5bfba38` (2b,
    "split off by default until K550 parity").
- **K551.** `detectGapSplit` and the pre-pass system's `contextChange`
  still set `fabric_sdf`'s `GAP_SPLIT` from capability. So from
  2026-10-18 every half-float GPU drew through the split, and on the
  desktop (D3D11, dsf 1.5) it drew NO crossing gaps at all. This was
  Levi's Daily #8 screenshot.
- **`f18dd07` keeps the split dark:**
  - only the renderer's `setGapSplit` (the probe A/B) turns it on;
  - the pre-pass's framebuffer check may still clear it;
  - the warm-up selects with the draw path's flag (`warmupContext`).
  - Read its message and diff first.
- **The probe A/B path** (`setGapSplit`, used by K320 stage 2 and K550's
  probes) drew gaps, with parity diffs in the thousands of pixels
  (`.claude/probes/K320/k550_diagnosis.md`), never "all gaps missing".
  The capability path drew none. **Why is undiagnosed.**
- **K320 2c** (shipping the split) waits on this and on K550, the parity
  blocker: a two-keep mask WIP patch and MSAA edge coverage. K550 is a
  later stage, out of scope here.
- **Evidence so far:** `.claude/probes/K551/`.
  - `gaps_check.mjs` is the headed probe template;
  - `out/` holds shots before the fix, `out_fix/` and `out_live/` after;
  - `out_live.log` records `gapSplitMode`, the pre-pass renders and
    warm-up wave 1 from `__knotRenderer()`.
  - On the fixed build the pre-pass renders 0 times with the split off.

## The question

On the broken build (`f18dd07^`), with the split on through capability,
why does the frame draw no crossing gaps, while `setGapSplit` on the
same build draws them?

## Hypotheses to test (not findings)

- **(a) The mask never rendered:** 0 pre-pass renders under the
  capability path, so the paint read an empty or cleared mask. Possible
  causes: the pre-pass is armed only by `setGapSplit`, or `contextChange`
  set the flag before the pre-pass system existed, or before a scene
  did.
- **(b) The warm-up linked a different program variant** from the one
  the frame used, and the frame sampled an unbound or stale texture.
- **(c) The framebuffer check passed** but the mask's format or
  precision behaves differently on D3D11/ANGLE.
- **(d) A transform or ordering mismatch:** the mask rendered with a
  stale view, so its gaps landed off the threads (K550 found a one-row
  offset in the shipped mask; a larger one would read as "no gaps").

  flips only that factor.
