# K100: the fog of war resets on a restart only (one stage)

Levi, 2026-10-13: "The fog should reset when the maze restarts. But the
fog shouldn't reset if we just backtrack to the start."

## What happens today

- `FabricMazeRenderer.update()` (`src/render/fabric_maze_renderer.ts`,
  the block commented "Reset path: the fog's explored memory starts over
  too") clears `fogStamps` whenever `controller.pathEdges` is empty. So
  walking back to the entrance by hand, a daily's Reset path (a
  backtrack: `FabricMazeController.retreatToStart`, K47; see
  `resetPathAction` in `src/game/daily_attempt.ts`) and a real restart
  all clear the fog alike.
- `exploredRuns()` (`src/game/daily_attempt.ts`) mirrors that rule for a
  saved attempt: the runs crossed since the path was last empty. main.ts
  hands them to `fabric.restoreExplored(...)` when a saved daily attempt
  comes back (`pendingExplored`).
- K80's catch (`FabricMazeController.respawn()`) empties the path but
  keeps the taps, and its lore says the explored fog stays. Find what
  keeps it today and keep that behavior.

## Goal

- The fog's explored memory resets only when the solve restarts: a
  `FabricMazeController.reset()` (Reset path where `resetPathAction`
  says "restart", Play again, a rebuild or a new design, K80's Reset
  path) and nothing else. A backtrack to the entrance, by hand or by a
  daily's Reset path, keeps it, and so does a K80 catch.
- A suggestion, not a requirement: `reset()` empties `taps` and nothing
  else does, so the explored runs could become every tap since the
  restart (`c.taps`), and the renderer could key its reset on the solve
  restarting instead of on the path emptying. Pick the cleanest signal
  and say why.
- K47's saves and replays must agree with live play: an attempt restored
  after a backtrack to the entrance shows the fog the live page showed
  before the reload.
- Memory-trail mode (no backtracks) and fog off behave as before.

### Calls (Levi was away)

1. The signal is an explicit restart counter compared edge-triggered,
   not a level test. "taps empty" misses a reset followed by taps before
   the next update(), which is what replay() does, and "path empty" was
   the bug.
2. `exploredRuns` returns every tap, duplicates kept: each pass of a run
   stamps it again in live play, so a restore must too.
3. A daily's Reset path stamps the runs it retraced live. Its jump back
   to the entrance does not animate, so without this the live fog would
   lack the way back that a restore of the same taps draws.
4. A catch uses `stopMove`, not `cancelMove`, because `cancelMove`'s
   finishFogArc would uncover the rest of a run the caught dot never
   reached.
5. No separate pure renderer rule: the counter is the rule and is tested
   in the controller; `travelOrder` and `moveEnds` are the pure, tested
   direction rules.
6. `restoreExplored` is renamed `exploreRuns`: it also serves the
   retreat now.
7. The fog-fit camera keeps framing everything explored after a
   backtrack (`fogVisibleBounds` reads the stamps). It used to close in
   on the entrance. This follows from the goal, and I kept it.
8. Scenario 3 runs on a probe server whose daily has the fog
   (`vite.fogdaily.config.ts`, an in-memory transform; the source on
   disk is untouched), because real dailies have the fog off and
   fogOfWar is not daily-exempt. The real daily is checked as
   `dailyoff`, and the static variant gives the exactness proof.
9. Restores and retreats stamp in travel direction. The brief requires
   restores to agree with live play; stamping A -> B did not (0.947
   against 0.977 with physics, 0.968 against exact on the static daily).
10. The physics checks pass at IoU 0.95 on one page and 0.9 across a
    reload, and travel must beat A -> B. Live stamps land over seconds
    while the threads move, so exact agreement is possible only on the
    static daily, where the checks require it.
