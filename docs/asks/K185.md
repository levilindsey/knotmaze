## Question
In a browser that had never drawn it, switching Reduced motion on stalled the page for about a third of a second, once, while the shader that draws the still pluck was built. Do you accept that, or should it be hidden or paid at load?

## Context
- Reduced motion swaps the moving pluck blur for a still picture with its own shader program. Measured on 2026-10-14 (K104): on a browser whose GPU cache had never seen the program, the first switch stalled one frame for 317 to 367 ms (three runs). A later switch or a reload cost 5 to 8 ms, because the browser keeps the compiled program per profile.
- Since then the shader warm-up (K307) links every program the page might draw, this one included, in the background once the intro is over, in browsers that support parallel compiling; others link at first use, as before. So the switch probably finds it ready. Nobody has timed the switch on today's build, which is why this is not closed outright.

## Options
- **Accept it (rec)**: nothing to build. It happens once per browser profile, only on a deliberate switch (or a system reduced-motion change) before the warm-up has run.
- **Link it in the background** (`KHR_parallel_shader_compile`): no stall, but it needs a hand-written GL pre-link of the same shader sources, because pixi links synchronously. The brief calls that fragile.
- **Warm it at load for everyone**: no stall, but +340 ms on every cold load. The brief calls that a bad trade.

## How to check
1. In a fresh browser profile, open the link and wait a few seconds after the maze appears.
2. Tick Reduced motion in the Accessibility folder: a stall shows as the picture freezing for about a third of a second. No freeze means this is moot.
